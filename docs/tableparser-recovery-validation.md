# Проверка восстановления после сбоев — 9 октября 2026

Ручной сценарий загрузки, ревью, публикации и реальной рассылки подтверждён
владельцем стенда. Этот этап отдельно проверяет отказы и повторы.

## Окружение

Отдельные временные PostgreSQL 16 и Redis 7 без внешней сети. База
`test_tableparser_validation`; worker использует только тестовый брокер.
Образ `eazyclass-parser-sandbox:delivery-v1`, тестовые настройки без токенов.
Отправители Telegram подменены. Рабочий локальный стенд с реальной рассылкой
не останавливался, его база и подписки не изменялись.

Результат: **49 тестов прошли**, включая две новые проверки восстановления
административного отчёта и принудительное завершение worker. Изменений рабочего
кода для прохождения этого этапа не потребовалось.

## Сценарии и действия администратора

| Ситуация | Ожидаемое поведение | Как продолжить |
|---|---|---|
| Один лист не загрузился | Частичный запуск не сохраняется | Повторить загрузку источника; все листы загружаются заново |
| Парсер завершился с ошибкой | Попытка `failed`, неполной выгрузки нет | Повторить разбор сохранённого запуска |
| Процесс парсера потерян | Попытка остаётся `running` | Убедиться, что worker остановлен, пометить попытку через `abandon_attempt`, повторить разбор |
| Повтор уже успешного разбора | Возвращается прежняя версия парсера | Исправленная администратором версия не перезаписывается |
| Применение расписания оборвалось | Транзакция не оставляет частичного результата | Возобновить ту же публикацию по UUID |
| Расписание применено, цепочка прервана | Повтор не применяет его заново | Возобновить ту же публикацию; продолжатся незавершённые этапы |
| Результат отправки неизвестен | Доставка `uncertain` либо `sending`, повтор заблокирован | Проверить исход; явно выбрать `retry` или `skip`, затем возобновить |
| Уведомления отправлены, отчёт упал | Уведомления остаются `completed` | Восстановить только этап `report`; уведомления повторно не отправляются |
| Восстановление запущено повторно | Завершённые этапы не повторяются | Использовать прежний UUID публикации |
| Два оператора восстанавливают одну попытку | Устаревший токен отклоняется | Перечитать текущее состояние |

Команды и условия выбора решения: [восстановление доставки](tableparser-delivery-recovery.md).
Повторная публикация кнопкой создаёт новую операцию: для продолжения оборванной
нужно возобновлять существующую, а не создавать новую.

## Границы проверки

Принудительная остановка проверяется на отдельном Celery solo-процессе с Redis
после имитации внешней отправки. Это не проверка аварии prefork-пула и не доказательство
доставки «ровно один раз»: Telegram и база не участвуют в одной транзакции.
При неизвестном исходе ручной `retry` может повторить уже полученное сообщение.
Завершённая частичная рассылка не повторяется целиком автоматически.

После восстановления используются сохранённые версия и границы публикации,
но подписчики выбираются по текущей базе. Отдельного GUI восстановления пока нет;
доступны служебные команды и читаемая история в админке.

Журнал изолированного прогона: `tableparser-releases/recovery-checks.log`
(локальный файл, не добавляется в Git).
