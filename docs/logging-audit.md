768/256/512 MiB, CPU 0.75/0.25/0.5 ядра, без дополнительного swap. Окружение

Оба варианта Compose проходят `config --quiet`, Alloy и Loki — свои валидаторы.

Окно подхвата расширено с 55 минут до 5ч55м. `ingester.max_chunk_age=12h`
разрешает Loki принимать внеочередные записи с запаздыванием до 6 часов.
Повторы отправки увеличены с 20 до 120 с паузой до 30 секунд. Дисковой очереди
Alloy по-прежнему нет, гарантии отсутствия потерь при аварии нет.

Production-лимиты проверены на локальном стеке с временным override, сохраняющим

через Grafana → Loki и из Docker, и из файла. Записи «семь часов назад» не поступили.
Контейнеры работали в лимитах без обнаруженного OOM: один замер Loki ~74 MiB,
Alloy ~51 MiB, Grafana ~281 MiB. Это smoke-проверка, а не замер production-пиков.
Тестовые контейнеры удалены, локальный стек возвращён к базовым лимитам
(без production-override). Приложение и сервер не перезапускались.

Инструкция [production](../observability/PRODUCTION.md) описывает запуск,

## Окончательное решение после обсуждения — 2026-09-30

Этот раздел описывает текущую конфигурацию; ниже сохранены результаты предыдущих
проверок, включая промежуточный вариант с категориями маршрутов.

- Основной production access-log — nginx в JSON. Поле `url` содержит исходный
  путь и query (`$request_uri`), вместо категорий `api/admin`. Referer, User-Agent,
  Authorization и Cookie отдельно не записываются. Query не очищается: это
  осознанный выбор, а не гарантия отсутствия чувствительных значений в URL.
- Сохранены статус, размер ответа, длительность, upstream-диагностика и
  request_id из ответа Django. Время nginx измеряется в секундах; Django — в мс.
- Итоговый HTTP-лог Django перенесён на DEBUG, поэтому при LOG_LEVEL=INFO не
  дублирует nginx. Контекст request_id, заголовок ответа, события приложения
  и диагностика ошибок остаются. Включение DEBUG на production вернёт HTTP-записи
  Django; это управление уровнем, а не жёсткое разделение окружений.
- Ошибка, вышедшая непосредственно из middleware, по-прежнему даёт ERROR.
  Штатные ответы 4xx/5xx дают access-запись DEBUG; их диагностические события
  сохраняют собственные уровни.
- Gunicorn access-log выключен; error-log сохранён. Лимиты Docker описаны ниже.

Окончательный JSON-формат проверен в отдельном nginx: nginx -t, ответы 200/502,
исходный URL с параметрами, передача request_id от тестового upstream, отсутствие
Referer/User-Agent. В этом повторном тесте использована HTTP-обвязка с локальными
upstream и точным log_format из рабочего файла; SSL-конфигурация проверена ранее.
Production не изменялся. Для всех логов nginx по-прежнему действует ограничение:
чувствительные данные в URL попадут в access-log и могут попасть в error-log.

JSON выбран для структурированного сбора. Компактное отображение этих полей в
Grafana будет отдельной настройкой, не поводом менять формат хранения на текст.

## Certbot: вывод cron и обновление установки

renew_tls.sh запускает временный контейнер с --rm; cron сохраняет stdout/stderr
в /var/log/certbot-renew.log на хосте. Docker-ротация certbot не ограничивает этот
файл. Добавлены certbot/logrotate.conf (weekly, 8 архивов, compress/delaycompress)
и install_renewal.sh для перезаписи существующего файла cron и установки ротации.
Установщик не запускает операции с сертификатами. Bootstrap вызывает его после
первоначальной настройки; отладочная печать переменных из bootstrap удалена.

Renew пишет время начала, этапы, итог и код ошибки. Перед reload выполняется
nginx -t; ошибки не подавляются. Успех проверки не означает фактического продления
сертификата. В nginx возвращён исходный закомментированный HTTP-only server для
ручного первоначального получения сертификата.

Проверка: bash -n и 6 Linux-тестов с подменёнными docker/sudo, включая сбои renew,
проверки nginx и reload, а также повторную установку cron без дублирования.
Фактические /etc/cron.d, /etc/logrotate.d и сертификаты не изменялись.
Инструкция production: certbot/README.md. Наличие и запуск logrotate на сервере
нужно проверить; конфигурация сама не устанавливает пакет и не включает таймер.

## Проверено на работающем Django

Контейнеры запущены пользователем через docker-compose.dev.yml. Django работает
через runserver; nginx в локальном составе не запущен. Проверочные HTTP-запросы
выполнены из контейнера к 127.0.0.1:8000, без изменения данных.

| Сценарий | Результат |
| --- | --- |
| Swagger | 200, одна итоговая HTTP-запись |
| Публичная схема | 200, прежние предупреждения HMAC и типов фильтров отсутствуют |
| Неверная дата в фильтре занятий | 400, понятная причина отказа и итоговая HTTP-запись с параметрами |
| Личное расписание без авторизации | 401, причина отказа и итоговая HTTP-запись |
| Занятия по дате и номеру | 200, параметры видны в query |
| Повтор с If-None-Match | 304, параметры и новый request_id сохранены |

X-Request-ID из ответов совпадает с идентификаторами диагностических записей.
DEBUG показывает проверку HMAC и ETag; итог HTTP остаётся на INFO. Две записи при
отказе имеют разный смысл: причина отказа и результат HTTP. Отдельного сообщения
о фильтрации занятий нет. В route виден завершающий `$` маршрутов DRF: это шаблон
из resolver_match, а не фактический URL клиента.

## Gunicorn и nginx

В Django-контейнере временно запущен отдельный Gunicorn с одним worker на
127.0.0.1:18081. После каждого опыта этот процесс остановлен; основной runserver
не перезапускался. С `--access-logfile -` один запрос Swagger дал две записи:
нашу HTTP-запись и стандартную Gunicorn. Без этого аргумента — одну. Проверена
команда с тем же WSGI-приложением, но это не полная production-среда с DEBUG=False
и тремя worker.

Из docker-compose.yml удалён `--access-logfile -`. Error-log и уровень Gunicorn
сохранены. Изменение вступит в силу при пересоздании production Django-контейнера.
Production не изменялся и не перезапускался.

nginx проверен только по конфигурации. Его access-log сохраняется: он показывает
редиректы, статику и ошибки проксирования, в том числе не дошедшие до Django.
Стандартный combined-формат содержит URL с query и Referer: фильтрация параметров
в Django на него не распространяется. Перед выкладкой нужно отдельно согласовать
безопасный состав nginx access-лога и проверить его на запущенном nginx.

## Фоновые процессы и автоматические проверки

- 142 теста общего набора логирования и API-схемы прошли в локальном venv.
- 71 тест прошёл внутри Linux-контейнера celery_worker: уведомления, контекст,
  форматирование, Scrapy/синхронизация и бэкапы.
- Celery chain/retry проверялись с отдельным worker и брокером в памяти,
  без публикации задач в рабочие очереди Redis.
- Scrapy проверен в отдельных процессах, включая локальный сценарий таймаута
  и повторов; перенос контекста SpiderRunner также покрыт тестами.
- Telegram подменён: проверены успех, ошибки, повторы, промежуточный прогресс
  и отсутствие чувствительных значений. Реальные уведомления не отправлялись.
- Синхронизация и бэкапы проверены изолированно; боевые данные расписания,
  Google-файлы, удалённые дампы и расписание Beat не изменялись.

Это проверка логирования, а не успешного полного сбора внешнего сайта или
доставки реальной рассылки. Подлинность результата внешних сервисов этими тестами
не подтверждается. JSON и INFO/DEBUG проверены тестами настройки отдельных
процессов; фактические HTTP-примеры выше получены в локальном текстовом формате.

Из известных предупреждений тестовой среды остаются неизвестная pytest-настройка
asyncio_default_fixture_loop_scope и deprecation полиморфного JSON:API-сериализатора.

Следующий шаг: безопасный формат nginx и правила хранения/ротации, затем
централизованный сбор. В production Compose лимиты Docker json-file уже заданы;
в dev Compose явных лимитов нет. Фактический объём и настройки диска ещё не измерялись.

## Продолжение проверки — 2026-09-30

Предыдущие выводы о nginx/dev-ротации выше отражают состояние до этого этапа.

Добавлен JSON access-лог nginx: время, сервис, событие, метод, категория маршрута,
статус, длительность в секундах, объём тела ответа, статус/время upstream,
request_id из ответа Django и собственный proxy_request_id. Если запрос не дошёл
до Django, request_id отсутствует (nginx отображает `-`), но proxy_request_id есть.
upstream-поля — строки, поскольку могут содержать несколько попыток или `-`.
Query, Referer, IP, User-Agent, Authorization и произвольные сегменты URL в access-лог
не включены. Точный API-маршрут и разрешённые параметры остаются в Django.
Существующие `access_log off` для статики сохранены. Формат задан в каждом server,
чтобы не оставлять параллельный унаследованный combined access-log.

На официальном nginx:alpine (digest
`sha256:df221db836e1754089190208cee7eeda94f233197056426eda74a43ab1abeac2`)
выполнены nginx -t и запросы 301/502. Использованы временный сертификат, случайные
порты только на 127.0.0.1 и локальные неработающие upstream. Получены ровно две
валидные JSON-записи без тестовых чувствительных маркеров. Временный контейнер
и сертификат удалены. Настоящие сертификаты и production не использовались.

**Ограничение:** штатный nginx error-log при 502 содержит исходный запрос, включая
query. Это подтверждено тестом. Пользовательский log_format действует только на
access-log и не очищает error-log. Ошибки nginx не отключены. При подключении
централизованного сбора нужна отдельная обработка error-log и ограничение доступа;
очистка при пересылке также не удалит исходные строки из локальных Docker-логов.

В dev Compose добавлены лимиты json-file 10m × 3 для каждого из шести сервисов;
в production добавлен ранее отсутствовавший лимит certbot 5m × 3. Прочие
production-лимиты сохранены. Ориентир бюджета: dev 180 МБ для шести контейнеров,
production 247 МБ для восьми; это приблизительный объём вращаемых логов, не
жёсткая дисковая квота и не срок хранения в днях. Образы, volumes, старые контейнеры
и служебные накладные расходы в этот бюджет не входят.

Оба Compose-файла прошли `docker compose ... config --quiet`. У действующих
локальных django/worker/beat/postgres/redis проверен json-file с пустым Config:
новые лимиты к ним ещё не применены. Для применения требуется пересоздание
контейнеров, а не restart; пересборка образов ради этих лимитов не нужна.
Контейнеры автоматически не пересоздавались, чтобы не прерывать ручные проверки.

Источники: [nginx log_format](https://nginx.org/en/docs/http/ngx_http_log_module.html),
[Docker json-file rotation](https://docs.docker.com/engine/logging/drivers/json-file/).
