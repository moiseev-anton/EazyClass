## Целевая организация

- TableParser остаётся отдельным репозиторием с общим ядром разбора.
- Локальные команды и локальный GUI сохраняются; локальная память — SQLite.
- Серверная память парсера — отдельные таблицы Django в PostgreSQL EazyClass.
- Пакет TableParser — способ установить конкретный выпуск кода, а не второй
  репозиторий и не хранилище рабочей базы знаний.
- Django-модели, Celery-задачи, серверный GUI и PostgreSQL-адаптер находятся
  в EazyClass. Ядро TableParser не импортирует Django-модели.
- Сервер читает все записи справочников через Django, включая неактивные.
  Набор фиксируется только в памяти на время разбора. Постоянные копии и новые
  версии справочников не создаются. После изменения справочников точное
  воспроизведение прежнего разбора не гарантируется; старый переносимый архив
  сохраняется для проверки миграции.
- Обученные модели, исходные снимки и крупные артефакты лежат в постоянном
  файловом хранилище. PostgreSQL хранит ссылки, хеши и метаданные.
- Docker нужен для проверки серверного окружения; обычный локальный запуск
  остаётся доступным без Docker.

После переключения сервер становится источником рабочих подтверждений.
Локальные эксперименты используют экспортированный снимок знаний. Локальные
изменения не вливаются обратно в рабочую память автоматически.

## Неизменные правила публикации

1. `needs_review` не препятствует публикации. Администратор проверяет уже
   опубликованные данные и явно запускает синхронизацию исправленной выгрузки.
2. На синхронизацию передаётся вся выбранная версия, а не только исправления.
3. Семантика периода остаётся текущей: `(0, None)` — с сегодняшнего дня без
   верхней границы, `(1, None)` — с завтрашнего дня без верхней границы.
   Для переданных групп отсутствующие занятия внутри периода удаляются,
   включая ноябрьские занятия при входной выгрузке только за октябрь.
   Покрытие датами исходной таблицы не ограничивает область удаления.
4. Границы периода фиксируются на запуск; повторы задачи используют те же даты.
5. Любую сохранённую выгрузку, включая старую, можно опубликовать вручную.
   Интерфейс показывает группы и период. Защита от запоздавших автоматических
   задач не должна запрещать осознанную ручную публикацию старой выгрузки.
6. При первой и повторной публикации используется обычная рассылка изменений.
   Существующий административный отчёт дополняется счётчиками и ссылкой.
7. Сохранение выгрузки и её публикация не создают подтверждения для ML.
   Сохранение правок, применение подтверждений и публикация — отдельные действия.
8. Ошибка получения не считается успешно полученным пустым расписанием.
9. Листы объединяются. Отдельная система приоритетов источников сейчас не нужна;
   автоматическое разрешение конфликтующих дубликатов не считается гарантией.

## Ближайший этап 1: воспроизводимый комплект состояния

Работа в TableParser; без подключения к публикации EazyClass.

Подготовить инструмент экспорта/проверки переносимого состояния:

- согласованная копия `knowledge.sqlite3` средствами SQLite, а не копирование
  потенциально изменяющегося файла;
- активные модели и все используемые ими дополнительные файлы, включая историю
  преподавателей; выбор по конфигурации, без выбора «последнего» каталога;
- правила замен/исключений, решения по предметам и настройки предложений;
- идентификатор кода, хеши рабочих исходников и артефактов, версии зависимостей,
  версия схемы БД, счётчики записей и проверка ссылок между ними;
- отдельное описание материалов дальнейшего обучения: разметка, исходные
  наборы, рецепты/параметры обучения и протоколы оценки;
- отсутствие `.env`, SSH-ключей, паролей и настроек доставки в переносимом
  комплекте; настройки доступа передаются отдельно;
- новый каталог результата, без перезаписи исходных знаний и старых комплектов.

Незакоммиченные offline-эксперименты не включать в рабочую цепочку. Исправление
года уже выполнено отдельно; перед созданием эталона явно зафиксировать его
версию. Один Git-коммит не описывает незакоммиченное рабочее состояние, поэтому
манифест должен учитывать хеши реально используемых файлов.

Критерий завершения: комплект можно проверить и открыть в изолированном
окружении без обращения к исходной рабочей папке. Перенесены знания, отзывы
подтверждений и происхождение записей; модели не переобучались.

Выбрать контрольные исходные снимки, охватывающие обычные занятия, предложения
моделей, подтверждения, части пары, подгруппы и примечания. Отдельно сохранить
синтетические проверки перехода года.

Зафиксировать входы, состояние знаний, модели, настройки и время, на которое
история доступна. Сравнивать конечные занятия, статусы/причины review и основания
подстановок. Исключать из сравнения только явно перечисленные служебные значения

Запуск не должен обновлять справочники, импортировать новые наблюдения,
сохранять подтверждения, отправлять файлы или уведомления.

Критерий завершения: обычный локальный запуск и запуск на переносимом комплекте
дают одинаковые содержательные результаты. Сохранён машиночитаемый отчёт.

## Django и перенос памяти: состояние этапа

Предыдущие этапы проверены; пункты 2, 3 и 5 выполнены для исторического снимка.
Пункт 4 реализован отдельным адаптером, подключение в серверную цепочку впереди.
Пункт 1 остаётся следующим:

1. Добавить приложение, например `schedule_ingestion`, с сущностями источников,
   запусков, снимков, версий выгрузок, review и публикаций.
2. Добавить таблицы памяти, заменяющие SQLite: наблюдения, архивное происхождение,
   подтверждения, их отзывы, соответствия и необходимые исторические данные.
   Одних таблиц запусков и выгрузок для замены SQLite недостаточно.
3. Реализовать PostgreSQL-адаптер интерфейса знаний и повторяемый импорт.
   Сохранить ID либо явное сопоставление ID для всех связанных записей.
4. Подключить справочники через Django, сохранив работу с неактивными записями,
   неоднозначными именами и историей. Проверить совместимость идентификаторов
   преподавателей с событиями моделей.
5. Сравнить PostgreSQL- и SQLite-реализации на одном эталоне и одинаковых снимках
   справочников. Переключение выполняется после совпадения результатов.

Существующий исторический архив сохраняет статус наблюдений. Ужесточение
правил использования старых наблюдений — отдельное изменение алгоритма,
не скрытый побочный эффект переноса. Новые непроверенные выгрузки не должны
автоматически пополнять этот архив или обучающие данные.

- Django GUI с защитой от устаревших правок, сохранением версий, отдельными
  подтверждением для памяти и повторной публикацией.
- Настройка периодических цепочек через django-celery-beat; времена выбираются

- Проверка в Docker с PostgreSQL, пробные запуски без публикации, затем ручное
  включение и периодичность. Не запускать два автоматических способа обновления
  одного источника одновременно при переходе.

## Выпуски и обновления

Код, модели/правила и схема знаний имеют отдельные версии совместимости.
Проверенный выпуск фиксирует их сочетание. Рабочая память живёт на постоянном
хранилище и не заменяется исходной SQLite при каждом обновлении приложения.

Перед выпуском выполняется сравнение на эталоне и свежих снимках. Переобучение
не запускается автоматически от подтверждений. Предыдущие комплекты сохраняются;
для изменений схемы БД отдельно определяется порядок миграции и отката.

## Ограничения текущего этапа

Сейчас разрешены проектирование, локальная подготовка и проверки. Синхронизация
производственного расписания, отправка сообщений и деплой не выполняются.
Все изменения EazyClass ведутся в указанной отдельной ветке; существующие
пользовательские изменения в обоих репозиториях сохраняются.
