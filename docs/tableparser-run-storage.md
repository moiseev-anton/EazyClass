# Хранение запусков и версий выгрузок

Реализовано 7 октября 2026 в ветке `codex/tableparser-integration`.
Миграция `0002_schedulesource_sheetcontent_parserun_exportrevision_and_more`
добавляет пять моделей без изменения scheduler и его синхронизации.

- `ScheduleSource`: идентификатор Google-таблицы, список листов, название и включение.
- `ParseRun`: UUID запуска, конфигурация источника на момент сохранения, дата
  исходных данных для определения года, время получения, `knowledge_as_of`,
  переданный манифест кода/ресурсов и номер последней версии.
- `SheetContent`: содержимое строк листа, однократно на SHA-256.
- `RunSheet`: полный упорядоченный состав листов конкретного запуска.
- `ExportRevision`: UUID версии, номер внутри запуска, автор, причина,
  ключ повторного запроса, полное содержимое выгрузки и SHA-256.

Это хранение исходных листов и результатов. Копии справочников здесь не создаются.

## Входные данные

`record_inputs` принимает успешно полученные листы по именам. Набор обязан точно
совпадать с конфигурацией источника: отсутствие листа, `None` вместо строк и
лишний лист отклоняются. Пустой список означает явно успешно полученный пустой
лист. Функция не получает данные по сети; будущий загрузчик обязан отличать
ошибку получения от пустого результата и проверять конфигурацию, с которой
начиналась загрузка.

Сохранение атомарно. Одинаковые строки дедуплицируются, но каждый запуск всё
равно содержит ссылки на все листы, включая неизменившиеся и пустые. Изменение
настроек источника впоследствии не меняет входы уже записанного запуска.
`load_tables(run_id)` проверяет состав и хеши и возвращает `RawTable` для пакета.
Дата для определения года передаётся явно, не вычисляется при повторном чтении.

Манифест пока является переданными метаданными: проверка фактического выпуска и
хешей ресурсов будет частью исполнителя разбора. `knowledge_as_of` не является
полным снимком знаний и не меняет исторические правила отзывов подтверждений.

## Версии после разбора и ревью

`save_export` принимает полный набор `groups`, `lessons`, `review_items`,
ожидаемый номер предыдущей версии и UUID запроса. Первая версия ожидает номер 0.
Каждая следующая версия хранится целиком, предыдущая сохраняется.
Устаревший редактор получает `StaleRevision`. Блокировка запуска PostgreSQL
защищает номер версии при конкурентной записи. Повтор с тем же UUID и теми же
данными возвращает прежний результат, в том числе после дальнейших правок;
повторное использование UUID для другой правки отклоняется.

`needs_review` сохраняется без запрета записи. Группы сохраняются отдельно от
занятий: пустая группа не исчезает из выгрузки. Занятие вне указанного состава
групп отклоняется. На этом уровне проверяется структура хранения, а не вся
предметная корректность занятия для синхронизации.

`load_export(revision_id)` возвращает именно выбранную версию с проверкой хеша.
Сохранение не запускает синхронизацию, рассылку или обучение, не создаёт
наблюдений и подтверждений. Старую версию можно адресовать явно; условия её
ручной публикации будут реализованы отдельным сервисом.

Сервисы не перезаписывают содержимое листов и выгрузок; обычный `save` существующих
записей запрещён. Это защита API приложения, а не запрет административного SQL.
Повреждение содержимого выявляется при чтении по SHA-256.

## Проверки и дальнейшее подключение

21 тест прошёл на PostgreSQL 16, включая ранее добавленные импорт и справочники.
Новые проверки охватывают полный состав листов при дедупликации, атомарный откат,
пустые листы и группы, правки с сохранением прежней версии, отсутствие обучения,
устаревшего редактора, повторы запросов, повреждение данных и конкурентные
сохранения из двух соединений. SQLite: 19 тестов прошли до добавления отдельной
PostgreSQL-проверки конкуренции, проверка MVCC пропущена.

Тесты используют изолированные настройки; рабочие миграции не применялись.
Проблема исторических миграций scheduler и согласование зависимостей пакета
остаются отдельно, как описано в `tableparser-postgres-memory.md`.

Далее: загрузчик с явными результатами получения, исполнитель разбора,
состояния ошибок/повторов и публикация по UUID версии. Для публикации нужны
согласованная блокировка с прежним путём синхронизации, фиксация периода,
защита от запоздавших автоматических задач и прежние уведомления. До этого
новые данные не передаются через общие Redis-ключи и не меняют расписание.
Период по-прежнему задаётся аргументами Celery; датами выгрузки не ограничивается.
