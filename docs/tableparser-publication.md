# Подготовка и применение выбранной версии

Реализовано 7 октября 2026 в `codex/tableparser-integration`.
Это сервис публикации; задачи рассылки и автоматическая цепочка ещё не подключены.

## Подготовка

`prepare_publication(revision_id, requested_by=..., automatic=False,
start_day_offset=0, end_day_offset=None, request_id=...)` фиксирует выбранный
UUID версии, режим, автора, даты периода и подготовленные данные синхронизации.
UUID запроса позволяет повторить подготовку после смены суток: даты остаются
прежними. Другие аргументы с тем же UUID отклоняются.

Группы сопоставляются с активными группами EazyClass по прежней нормализации
названия. Неизвестная или неоднозначная группа останавливает подготовку целиком.
Неактивные преподаватели доступны для сопоставления. При неоднозначном сокращённом
имени сохраняется исходный текст, как для неизвестного преподавателя, без
произвольного выбора одной записи. Данные готовятся до применения и сохраняются
с SHA-256. Наличие `needs_review` не является ошибкой и не исключает строку.

Проверяются даты, номер пары, `part`, `subgroup` и типы полей. Структурированные
`annotations` превращаются в строку тем же `annotation_text`, который использует
CSV TableParser; при отсутствии структуры допустимо скалярное `annotation`.
Различие последовательных частей и параллельных подгрупп сохраняется. Дальнейшие
default/truncate и создание связанных записей выполняет существующий менеджер.

## Применение

`apply_publication(publication_id)` работает с сохранённой подготовкой, без
общих ключей Redis. `LessonsSyncManager.update_from_data` принимает конкретные
группы и занятия; используется прежнее сравнение и применение изменений.

Расписание, связанные объекты, журнал обновления, summary и статус `applied`
сохраняются одной транзакцией. Ошибка оставляет `pending` и откатывает изменения.
Повтор `applied` возвращает сохранённый summary, не применяет расписание повторно.
Summary содержит обычные `added`, `updated`, `removed` для будущей рассылки.

Удаление действует по полному заданному диапазону для переданных групп.
Пустая выгрузка с группами очищает их период. Октябрьские входные данные при
неограниченном сверху периоде удаляют отсутствующие ноябрьские занятия.
Даты входных занятий не ограничивают область удаления.

## Конкурентные обновления

Старый `update_schedule` и новый вход используют общую транзакционную advisory
блокировку PostgreSQL. Сравнение с БД, изменение и сериализация больше не
разделены между конкурирующими writers. Блокировка глобальная: независимые группы
пока также синхронизируются последовательно. SQLite используется для обычных
тестов; конкурентные гарантии проверены на PostgreSQL.

Сигнал внутри транзакции сохраняет `ScheduleWriteEvent` с группами, диапазоном
и временем актуальности данных. Для автоматической публикации это время получения
её запуска; для ручной и старого импорта — время применения. Даже синхронизация
без изменений фиксирует подтверждённую актуальность проверенных групп.

Если более свежая запись журнала пересекается с группами и периодом автоматической
публикации, вся публикация получает `superseded` без изменения расписания.
Режим ручной публикации явно разрешает применить старую версию; событие такой
публикации также защищает её от ранее полученных автоматических выгрузок.
Запись применения старого импорта учитывается новой защитой.

Это не переделывает получение данных старой цепочкой: её общие Redis-ключи пока
сохраняются, а старые задания сами не получили идентичность запуска и проверку
свежести входов. Не следует включать два автоматических способа обновления
одного источника одновременно. Общая блокировка защищает транзакции обоих путей,
но не делает прежнюю загрузку через Redis адресованной по запуску.

Прямые SQL-правки расписания и иные пути, обходящие менеджер, в этот журнал
автоматически не попадают. Интерфейс публикации и проверка прав пользователей
будут подключены отдельно. Новую миграцию `0005` нужно применять до запуска
worker с подключённым обработчиком событий.

## Проверки и следующий этап

69 тестов прошли на PostgreSQL 16: приложение ingestion и прежние тесты диапазона
и аннотаций scheduler. Проверены удаление будущих занятий, пустые группы,
ограниченный период, `needs_review`, части/подгруппы, неактивный преподаватель,
аннотации, старые ручные версии, запоздавшая автоматическая публикация после
нового либо старого пути, откат, даты при повторе, повторная одновременная доставка
и блокировка между PostgreSQL-соединениями. На SQLite ранее прошли 63 теста,
4 специфичные проверки были пропущены. Рабочая БД не изменялась.

Следующий шаг — доставка уведомлений по сохранённому summary, административный
отчёт со ссылкой/идентификаторами и подключение публикации к Celery. Нужно отдельно
фиксировать период до запуска всей цепочки, чтобы долгий разбор через полночь
не менял границы. Записи beat и реальная рассылка сейчас не запускались.
