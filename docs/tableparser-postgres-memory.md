# Память TableParser в PostgreSQL

Проверено 7 октября 2026 года, ветка `codex/tableparser-integration`.

## Реализация

Приложение `schedule_ingestion` зарегистрировано в настройках EazyClass.
Начальная миграция создаёт отдельные таблицы памяти: наблюдения, происхождение
архивов, соответствия, подтверждения и отзывы, снимки справочников, ошибки
загрузки и исключения справочников. `KnowledgeImport` хранит контрольную сумму
и результат первоначального переноса. Рабочая БД проекта не мигрировалась.

Исторические JSON и строки времени сохраняются как TEXT, без нормализации:
их исходное представление участвует в сравнении подтверждений и происхождении
модельных решений. Дополнительные SHA-256 поля обеспечивают поиск и уникальность
без огромных B-tree ключей. Связи, исходные ID и ID отзывов сохраняются;
последовательности PostgreSQL после импорта устанавливаются на актуальные значения.

Команда `import_tableparser_knowledge PATH` по умолчанию только проверяет SQLite.
`--apply` выполняет перенос в транзакции; `--database` выбирает Django alias.
Поддерживается схема знаний v3. Источник открывается read-only и копируется
SQLite backup API для согласованного снимка, включая зафиксированные WAL-данные.
Проверяются целостность, таблицы, колонки, типы, JSON, даты и связи.

Первоначальное хранилище должно быть пустым. Импорт сверяет все поля каждой
перенесённой записи. Повтор с тем же содержимым сверяет записи и возвращает
`already_imported`; другой снимок или изменённые исходные записи отклоняются.
Новые серверные записи могут сосуществовать с первоначальными. Ошибка приводит
к откату записей и журнала импорта. Первоначальный импорт сериализуется блокировкой
строки журнала, исходная SQLite не используется для перезаписи памяти при обновлении.

`DjangoKnowledgeReader` реализует контракт `ParserKnowledge` через Django ORM.
Порядок результатов и существующие различия временных правил подтверждений,
ретроспективы и отзывов сохранены. Новые выгрузки автоматически не импортируются
в наблюдения, подтверждения или обучение.

`HistoricalCatalogReader` воспроизводит сохранённые справочники, включая накопленные
записи, происхождение и дополнительные локальные записи преподавателей. Это
читатель истории для проверки переноса. Серверный адаптер `load_live_catalogs`
читает актуальные модели EazyClass напрямую, включая неактивные записи.
Независимого редактируемого справочника на сервере нет.

## Актуальные справочники: уточнение 7 октября

По согласованному уточнению версии справочников на сервере не накапливаются.
Добавленные при подготовке `CatalogCapture` и миграция `0002` удалены до выпуска.
`load_live_catalogs(source=..., using='default')` возвращает `LiveCatalogReader`
с данными в памяти. Его `parser_services()` создаёт сервисы преподавателей и
кабинетов для `create_context`. После загрузки обращения к БД не требуются.

Все записи `Teacher` и `Classroom` читаются напрямую, без фильтра `is_active`.
Совпадения сокращённых имён обрабатываются прежними репозиториями как неоднозначные.
Удалённые из EazyClass записи не возвращаются из старых API-снимков. Пустой либо
некорректный справочник вызывает ошибку, без скрытого перехода к старым данным.

Импортированные локальные дополнения преподавателей с отрицательными ID пока
подключаются отдельно: они отсутствуют в EazyClass и являются собственными данными
парсера. Совпавшее полное имя из EazyClass имеет приоритет. Явные исключения
сохраняются. `source` должен соответствовать происхождению импортированных
исключений; это не адрес для сетевого запроса. Автоматического создания
преподавателей в EazyClass нет.

PostgreSQL загружается в короткой транзакции `REPEATABLE READ READ ONLY`.
Это согласованное чтение, а не сохранение версии: изменения во время загрузки
станут видны при следующем вызове. Внешняя транзакция запрещена, чтобы случайно
не использовать другое состояние изоляции. На SQLite используется обычная
транзакция чтения. Запросов записи адаптер не выполняет.

Старые импортированные снимки остаются для проверки исторического эталона и
не обновляются новым адаптером. Они не служат резервным текущим справочником.
Для точного повторения произвольного старого запуска после правок справочников
сохранения данных сейчас нет — это осознанное ограничение согласованного подхода.

Проверка: 13 тестов прошли на PostgreSQL 16; 12 на SQLite, один тест PostgreSQL
пропущен. Покрыты отсутствие записи и обращения к истории API, неактивные записи,
удаление и изменение записей между загрузками, локальные дополнения, исключения,
неоднозначные имена и конкурентная запись из другого соединения. Проверки
используют установленный wheel парсера и реальные модели scheduler в тестовой БД.
Настройки `catalog_settings` / `catalog_postgres_settings` создают текущие модели
scheduler/auth/contenttypes без старых миграций scheduler (их известная проблема
создания чистой БД остаётся отдельно); миграция schedule_ingestion применяется.

## Повторение проверки

Использовать отдельную временную PostgreSQL с БД и пользователем
`tableparser_validation`, паролем `local-validation-only`, доступную только
на localhost. Порт передать через `TABLEPARSER_TEST_PG_PORT`.
Настройки `schedule_ingestion.tests.postgres_settings` изолированы от `.env`
и рабочих настроек EazyClass.

1. Выполнить `python -m django migrate --settings=schedule_ingestion.tests.postgres_settings --noinput`.
2. Выполнить `python -m django test schedule_ingestion.tests --settings=schedule_ingestion.tests.postgres_settings --noinput`.
3. Импортировать снимок командой `python -m django import_tableparser_knowledge PATH --settings=schedule_ingestion.tests.postgres_settings --apply`.
4. Запустить `python -s -P -B -X utf8 -m schedule_ingestion.tests.replay_postgres`
   с `--source` (исходная knowledge.sqlite3), `--state` (внешние ресурсы
   проверенного package replay), `--baseline` (knowledge-reader replay)
   и `--output` (новая папка). Установить `PYTHONHASHSEED=0`,
   `OPENBLAS_NUM_THREADS=1`, `OMP_NUM_THREADS=1`; в путях импорта должны быть
   EazyClass и установленный пакет, без исходного корня TableParser.
5. Проверить `completed.json` и удалить временный контейнер.

## Границы готовности

Это проверка серверного хранилища, не готовая производственная цепочка.
Источники, запуски, версии выгрузок, ревью, публикации и Celery ещё не подключены.
Существующая синхронизация и её диапазон удаления не изменены.

SQLite сохраняется для локальных запусков. Обучающие файлы, в том числе
`extraction_labels.sqlite3`, и веса остаются внешними ресурсами переносимого
комплекта; перенос восьми таблиц runtime-памяти их не заменяет. Переобучения не было.

Зависимости проверялись с уже установленными библиотеками Windows, а не в чистом
серверном окружении. Перед выпуском нужно согласовать фиксацию python-dotenv
(EazyClass 1.2.1, пакет парсера 1.2.2), проверить совместную установку зависимостей,
внутренние top-level имена модулей и полный запуск приложения на Linux/Docker.
Проверка PostgreSQL в контейнере не заменяет эти проверки.
