# Ручная проверка TableParser локально

Стенд подготовлен и запущен. Открыть **http://127.0.0.1:18080/admin/**.
Логин: **parser-admin**. Пароль записан в локальном файле
`tableparser-releases/access.secret` (в Git не добавляется).

Это отдельная копия локальной БД EazyClass с PostgreSQL, отдельный Redis и worker.
В шапке admin написано «Локальный стенд TableParser · копия БД · рассылки отключены».
Исходная БД не меняется. Синхронизация действительно меняет расписание **стенда**;
обе фазы доставки получают `skipped`, сообщения и отчёты не отправляются.
Beat не запущен: автоматические периодические задачи из копии БД не выполняются.
Google Sheets загружается настоящим загрузчиком по явному действию администратора.

## Сразу попробовать ревью и повторную синхронизацию

1. Открыть раздел «Поступление расписания» → версии выгрузок (`Export revisions`).
   Выбрать последнюю версию демонстрационного запуска для группы **ТЕСТ-ПАРСЕР**,
   перейти по ссылке «Занятия и публикация».
2. Нажать «Опубликовать», указать начало `0`, конец оставить пустым.
   Проверить календарный период, затем подтвердить. Обновить страницу через
   несколько секунд: публикация должна перейти из `pending` в `applied`.
3. Нажать на строку карточки, изменить предмет/кабинет/другие поля,
   отметить «Строка проверена». Можно исправить сразу несколько карточек:
   общая кнопка «Сохранить изменения» создаст одну полную версию.
4. Опубликовать новую версию тем же способом. Проверить изменённое занятие в
   разделе Lessons, отфильтровав группу **ТЕСТ-ПАРСЕР**. Старая версия сохраняется.

Образец датирован **8 октября 2026**. Если проверка происходит позже, исправить
дату занятия либо задать начало периода соответствующим отрицательным сдвигом.
До передачи стенда уже выполнены две пробные публикации; их история оставлена.
В демонстрационной версии также оставлены связанные занятия для проверки редактора.
Источник «Демонстрация ревью (без Google)» выключен: у него нет реальной таблицы,
включать его для загрузки не нужно.

## Настроить настоящий источник Google Sheets

1. В `Schedule sources` добавить источник. В `spreadsheet_id` вставить часть
   ссылки между `/d/` и `/edit`. Таблица должна быть доступна публичному GViz
   endpoint; подключение закрытой таблицы через Google OAuth не реализовано.
2. В блоке листов для каждого листа заполнить название и gid. Кнопка «+» добавляет
   лист, кнопка удаления убирает его. Числа берутся из `gid=` в адресе вкладки.
   Указать все листы источника, включить `enabled`, сохранить.
3. В списке источников поставить галочку у нужного источника, выбрать действие
   **«Загрузить листы и разобрать расписание»**, нажать «Выполнить».
4. Перейти по ссылке «Открыть запуски» из сообщения. Обновить список после работы
   worker. Открыть запуск, затем созданную выгрузку. Здесь можно сначала
   опубликовать исходный результат (включая `needs_review`), затем провести ревью
   и отдельно опубликовать исправленную версию.

Загрузка не публикует автоматически. Повтор действия означает новое получение.
Если Google-загрузка завершилась ошибкой, запуск не создаётся; смотреть журнал
worker командой ниже. Ошибки парсинга видны также в попытках сохранённого запуска.
При сомнении в постановке задачи сначала проверить журнал, затем повторять.

Группы выгрузки должны однозначно сопоставляться с активными группами в копии БД.
Преподаватели и кабинеты читаются из неё, включая неактивные записи. Для групп
публикации отсутствие занятий очищает **весь указанный период**, как в основном
проекте. Сохранение правок и публикации не обучают модели и не пополняют память.

## Запуск и остановка

В PowerShell из корня EazyClassProject, при работающем Docker Desktop:

```powershell
./scripts/parser-sandbox.ps1 status
./scripts/parser-sandbox.ps1 stop
./scripts/parser-sandbox.ps1 start
./scripts/parser-sandbox.ps1 logs
```

Остановка сохраняет PostgreSQL в отдельном Docker volume. Не выполнять
`down -v`, если нужны ваши тестовые изменения. Web слушает только `127.0.0.1:18080`;
PostgreSQL и Redis наружу не опубликованы. Стенд использует Django runserver
со статикой, он предназначен для локальной проверки, а не серверного размещения.
Старые cookies основной локальной версии не конфликтуют: имена cookies отдельные.

Конфигурация: `docker-compose.parser-sandbox.yml`, настройки
`eazyclass/local_parser_settings.py`. Локальные секреты и пути находятся в
`tableparser-releases/compose.secret`. Образ: `eazyclass-parser-sandbox:gui-v8`.
Он основан на проверенном серверном worker; поверх добавлены действия admin,
режим пропуска доставки и настройки стенда. Пакет/модели парсера не менялись.

Ресурсы выпуска находятся в `tableparser-releases/0.1.1/`, вне каталога загрузок
`data/`. Скрипт управления предпочитает новый путь конфигурации, сохраняя
совместимость со старым `data/tableparser-sandbox/compose.secret`.
При обновлении GUI база стенда и пароль администратора сохраняются.

При подготовке нового стенда сначала создать отдельные реквизиты и volume,
восстановить снимок EazyClass именно в `tableparser_sandbox`, затем выполнить
`scripts/bootstrap_parser_sandbox.py` внутри контейнера с настройками стенда.
Скрипт проверяет режим/имя БД, применяет миграции, импортирует знания, создаёт
пользователя и пример. Повторно дамп в уже заполненную БД не восстанавливать.
Пустая БД не является заменой копии: в старой squashed-миграции scheduler есть
отдельные ограничения первоначального развёртывания.

## Проверено

- В итоговом окружении Python 3.12.15 все шесть архивных сценариев — **8670 занятий** —
  совпали с эталоном по занятиям, review, группам, CSV и sidecar. Runtime без SQLite,
  доступ к SQLite при разборе запрещён; память и ресурсы остались неизменны.
  Отчёт: `data/final-image-replay/replay/report.json`, SHA256
  `995c23520db0399ea67e3c116b34425613023aa82cef61a33bab35d9338c2721`.
- Полный ручной маршрут проверен через настоящий HTTP с CSRF, Redis и отдельным
  Celery worker: две публикации `applied`, четыре доставки `skipped`, исправленный
  предмет оказался в расписании. Знания не пополнились.
- Дополнительные тесты проверяют разрешения/CSRF действия загрузки, выключенный
  источник, отсутствие ресурсов, ошибку брокера и обе пропущенные доставки.
  Общий прогон после обновления GUI — **117 тестов, все прошли**;
  журнал `tableparser-releases/gui-checks/all-tests.log`.

При повторном `migrate` Django сообщает о старых отличиях моделей scheduler
(`Group.endpoint`, `Period.lesson_number`, `Teacher.endpoint`) от миграционного
состояния. Они не внесены интеграцией TableParser; миграции на них не создавались.
Восстановление существующей БД, чтение справочников и обе синхронизации проверены.
