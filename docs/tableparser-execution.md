# Исполнение сохранённого запуска

Добавлен `execute_parse` и management-команда `parse_saved_run`.
Исполнитель читает конкретный `ParseRun`, восстанавливает исходные листы,
загружает текущие справочники EazyClass в память, создаёт контекст с
`DjangoKnowledgeReader` и вызывает установленный пакет TableParser.
Результат сохраняется первой полной версией выгрузки. `needs_review` не мешает
сохранению. Синхронизация, рассылка и пополнение памяти не запускаются.

## Подготовка и вызов

До `record_inputs` сформировать манифест через
`runtime_manifest(resource_root, catalog_source=source)` и передать его как
`parser_manifest`. Источник справочника — пространство имён существующих
исключений, не адрес для HTTP-запроса. Для рабочего запуска он должен
соответствовать той же БД EazyClass, из которой получена импортированная память.

Манифест содержит версию Python, контрольные суммы Python-файлов установленного
пакета, версии перечисленных зависимостей и всех файлов отдельного каталога
ресурсов (кроме `__pycache__`). Это намеренно отдельный неизменяемый каталог
выпуска, а не рабочая папка CLI с постоянно меняющимися файлами. Ссылки на файлы
за пределами каталога отклоняются. Пути внутри настроек должны указывать на
ресурсы этого выпуска. Манифест фиксирует фактическое окружение, но не заменяет
согласование зависимостей и проверку совместимости перед выпуском.

Манифест проверяется перед разбором и перед сохранением. При несовпадении
версии/хеша сохранения выгрузки нет. Подмена уже загруженного Python-модуля
другим файлом обнаруживается по путям. Выпуск worker не следует обновлять
на месте: Python кеширует импортированные модули; после обновления нужен новый
процесс. Ресурсы также должны оставаться неизменяемыми во время работы.

Ручной вызов с явно выбранными Django-настройками:

```text
python -m django parse_saved_run RUN_UUID --resources RESOURCE_ROOT --catalog-source SOURCE --settings=SETTINGS
```

Команда выводит UUID созданной либо ранее созданной parser-версии. Старые
тестовые запуски с произвольными метаданными вместо нового манифеста исполнитель
отклонит; их следует оставить как тестовые данные, а для разбора создать новый
запуск с корректным манифестом.

## Попытки и повторы

Миграция `0003_parseattempt` добавляет журнал попыток. Под блокировкой запуска
создаётся `running`; второй исполнитель получает `ParseBusy`. Длительный разбор
выполняется без блокировки строки запуска. После разбора запись выгрузки и
переход попытки в `succeeded` совершаются одной транзакцией.

Обычная ошибка завершает попытку как `failed`. Хранится тип ошибки, без её текста,
который может содержать исходные данные. Ошибка передаётся вызывающему коду.
Следующий явный вызов может создать новую попытку. Автоматического бесконечного
повтора нет. Повтор после успеха возвращает первоначальную parser-версию, даже
если администратор уже создал следующую исправленную версию.

Потеря процесса оставляет `running`. Восстановление выполняется явно сервисом
`abandon_attempt(attempt_id)`: он помечает попытку `abandoned` и разрешает новую.
Запоздавший старый worker проверяет статус под блокировкой и не может сохранить
свой результат. Таймер, автоматически объявляющий долгую работу потерянной,
не вводился. Для будущего интерфейса восстановления потребуется проверка прав.

Если версия была создана отдельно до завершения парсинга, исполнитель её не
перезаписывает: `save_export(expected_revision=0)` отклоняет такую запись.

## Границы воспроизводимости

Справочники берутся на момент каждой попытки без постоянных копий. Изменения
справочников между неудачной попыткой и повтором могут изменить результат.
Время знаний берётся из запуска, но существующие различия временных правил
подтверждений сохранены; полного версионированного снимка PostgreSQL-памяти нет.
При успешном повторе готовая версия возвращается без нового разбора.

Проверки лёгкого тестового профиля используют установленный пакет с выключенными
модельными предложениями и без teacher ML pointer. Это проверка цепочки и ошибок,
не оценка качества моделей. Дополнительная проверка включается переменной
`TABLEPARSER_TEST_RESOURCE_ROOT` и использует существующий обученный комплект,
контролируя неизменность его файлов и запрещая `sqlite3.connect` во время разбора.

Проверено 7 октября: все 28 тестов прошли на PostgreSQL 16, включая запуск с
комплектом `package-replays/verified-2026-10-07/state`. Файлы комплекта не
изменились. На SQLite прошли 25 тестов цепочки; две PostgreSQL-проверки пропущены
(до добавления отдельного теста обученного комплекта). Проверка соответствия
миграций моделям и Django system check прошли. Рабочая БД не использовалась.

Следующий этап — получение листов с обработкой ошибок и изменившейся конфигурации,
подключение исполнителя в Celery и отдельный сервис публикации по UUID версии.
Период синхронизации и правила удаления отсутствующих занятий не менялись.
