# Логирование EazyClass

## Назначение и текущий этап

Логи должны объяснять результат конкретной операции: что произошло, где,
почему и в рамках какого запроса или фонового запуска. Метрики показывают
частоту событий и изменение показателей со временем; трассировки помогают
найти, на каком участке потрачено время.

Приняты правила ниже, удалены прямые записи чувствительных данных из
авторизации и отладочного HTTP middleware, исправлен уровень успешной
привязки nonce. Внедрены общий JSON/текстовый формат, отдельные поля событий
и безопасное представление стека. Внедрена передача идентификаторов между
HTTP, Celery и процессом паука. Метрики и централизованный сбор ещё не
внедрены. Остальные модули мигрируют постепенно.
Это не подтверждение отсутствия чувствительных данных во всех логах:
отдельно предстоит проверить библиотеки, Gunicorn, nginx, Celery и Scrapy.

## Выбор событий

Перед добавлением записи сформулировать вопрос, на который она отвечает.
Записывать значимые результаты, причины пропуска, частичные и полные сбои.
Для длительных операций нужен старт и итог. Для коротких запросов достаточно
итога. Успех записывать после завершения всех обязательных действий, для
изменений БД — после успешного завершения соответствующей транзакции.

В циклах предпочитать итоговые счётчики. Подробности по отдельным объектам
нужны при сбое или на DEBUG, с ограничением объёма. Не выводить целые DTO,
списки получателей, ответы API, HTML и содержимое файлов.

| Уровень | Когда использовать | Пример |
| --- | --- | --- |
| DEBUG | Детали для диагностики | Решение пропустить неизменившуюся страницу |
| INFO | Значимый нормальный результат или ожидаемый пропуск | Синхронизация завершена; подписчиков нет |
| WARNING | Деградация, частичный результат, повтор после временного сбоя | Источник недоступен, назначена повторная попытка |
| ERROR | Операция не выполнена, неожиданный сбой | Попытки исчерпаны; запись в БД не выполнена |
| CRITICAL | Серьёзная потеря работоспособности, требующая немедленного вмешательства | Критически необходимая подсистема не может запуститься |

Не считать любой 4xx ошибкой приложения. Отсутствие изменений и отсутствие
подписчиков — штатные исходы. Отсутствие HMAC-заголовков может означать выбор
другого способа аутентификации. Блокировка бота пользователем — отдельный
ожидаемый исход доставки, а не авария всего сервиса.

## Соглашение о записях

- Использовать `logging.getLogger(__name__)` и ленивую подстановку `%s`.
- Имя события стабильно, на английском, например `schedule.sync.completed`.
  Оно не содержит ID, адреса, пользовательского текста или меняющихся чисел.
- Основные поля JSON: `timestamp` (UTC), `level`, `logger`, `event`,
  `message`, `service`, `environment`.
- Контекст по необходимости: `request_id`, `task_id`, `run_id`, `duration_ms`,
  `outcome`, `reason`, `attempt`, `error_type` и числовые счётчики.
- `run_id` объединяет цепочку задач; `task_id` обозначает задачу; `attempt`
  различает её попытки. Передавать контекст явно через Celery и в процесс
  Scrapy, очищать его на границе каждой операции.
- Не использовать зарезервированные атрибуты LogRecord в `extra`.

Человеческое сообщение помещается в `message`, стабильное имя — в `extra.event`,
контекст — в другие поля `extra`. Например:

```python
logger.info(
    "Одноразовый код авторизации привязан к пользователю",
    extra={"event": "auth.nonce.bound", "user_id": user_id},
)
```

Не строить JSON вручную и не разбирать произвольный текст для метрик.
Новые поля должен поддерживать общий форматтер; текущий этап его внедрения
описан ниже. Код события не заменяет понятное объяснение человеку.

## Разрешённые и запрещённые данные

Правило действует на всех уровнях, включая DEBUG и локальную разработку.
Выбирать поля явно, а не записывать объект целиком с последующей маскировкой.

Запрещены пароли, секреты HMAC, подписи, access/refresh-токены, nonce, JTI,
cookies, Authorization, Telegram initData, токены ботов и URL с ними,
строки подключения с учётными данными. Не записывать полные заголовки,
тела запросов/ответов, query string, HMAC-вход и внешние профили пользователей.

Для HTTP использовать объявленный шаблон маршрута, метод, статус и
длительность. Если маршрут не определён, писать `<unresolved>`; не подставлять
сырой URL. Не включать значения параметров пути. Внешний текст и произвольные
заголовки не использовать как имя события или причину.

Внутренний `user_id` записывать в событиях пользователя, включая авторизацию;
он полезен для расследования и не является секретом входа. Доступ к логам
должен быть ограничен. Имена, social_id, chat_id, IP и другие
персональные данные не добавлять по умолчанию. Для рассылок использовать
счётчики; потребность в идентификаторе получателя обосновывать отдельно.

Секреты полностью исключать: не показывать последние символы, не вычислять
хеши или отпечатки. Для связи записей использовать безопасные идентификаторы
запросов, задач и запусков.

Тексты исключений и traceback также могут содержать секреты, включая цепочку
предыдущих исключений. В обработчиках авторизации используем
`safe_error_context(exc)` из `eazyclass.logging_config`: он сохраняет типы
исключений, имена файлов, функции и номера строк. Значения исключений,
локальные переменные, строки исходного кода и полные пути не сохраняются.
Порядок цепочки: текущее исключение, затем его причина/контекст. Лимиты:
8 исключений, последние 40 кадров каждого. Исходный объект исключения
не передаётся в LogRecord. Полная структура `error_stack` видна в JSON и
text_verbose; компактный text показывает тип и последнее место ошибки каждого звена.

Общий форматтер так же обрабатывает `exc_info` библиотек, не использует
закешированный `exc_text` и сырой `stack_info`. Это не очищает секрет,
который вызывающий код уже встроил в `message`: сообщения с `%s, exc` или
f-строками исключений предстоит заменить при миграции остальных модулей.
Для объяснения ошибки добавлять безопасный `reason`, а не произвольный
текст внешнего сервиса.

## Общая конфигурация

Конфигурация и форматтер находятся в `eazyclass/logging_config.py`.
Вывод идёт в stderr, одна запись на строку; время — UTC. Переносы строк
экранируются. Конфигурация не требует новых зависимостей.

| Переменная окружения | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `LOG_FORMAT` | `text` при DEBUG, иначе `json` | `text`, `text_verbose` или `json` |
| `LOG_LEVEL` | `INFO` | Уровень кода приложения; для диагностики установить `DEBUG` |
| `LOG_SERVICE` | `eazyclass` | Имя процесса; Compose задаёт django/celery-worker/celery-beat/flower |
| `LOG_ENVIRONMENT` | development при DEBUG, иначе production | Например, явно задать staging |

Scrapy-процесс получает service=`scrapy`. Пустые LOG_FORMAT и LOG_ENVIRONMENT
используют значения по умолчанию. Некорректный формат или уровень останавливает
запуск с ошибкой настройки. Переменные читаются при старте процесса.

Компактный `text` рассчитан на чтение в терминале. Например:

```text
12:30:01.234 [INFO] Одноразовый код авторизации привязан к пользователю | req=12345678 user_id=42
```

В `text` не повторяются имя модуля, service, environment и event; вместо всех
UUID показываются первые 8 символов run_id, либо request_id, если run_id нет.
Это подсказка для чтения, не гарантированно уникальный идентификатор. Остаются
прикладные поля пользователя/группы/HTTP, длительность и номер повторной попытки.
Полные идентификаторы и метаданные доступны в `text_verbose` и JSON.
Короткое время в text — UTC; полная дата есть в остальных форматах и Docker.

JSON сохраняет разрешённые данные с исходными типами, например `user_id` числом,
если вызывающий код передал число. Не мигрированные сообщения получают
event=`log.message`; новые события следует именовать явно.

`CONTEXT_FIELDS` — разрешённые поля `extra`. Неизвестные поля, включая nonce,
токены, заголовки и request, в вывод не попадают. Для новых полей расширять
схему после проверки назначения. Произвольные объекты не преобразуются через
str/repr; строки контекста ограничены 2000 символами. Поля не маскируются
«последними четырьмя символами» и не хешируются. Эта схема защищает вывод
extra; ответственность за безопасное содержимое message и разрешённых полей
остаётся на вызывающем коде.

Django и Celery используют один root handler. Сигнал Celery `setup_logging`
отключает его собственную настройку, а `worker_process_init` применяет общую
конфигурацию в дочернем процессе. Уровни задаются конфигурацией проекта;
параметры Celery `--loglevel`/`--logfile` её не переопределяют. Неактуальные
`--loglevel` удалены из Compose. Уровень Celery оставлен INFO, Scrapy WARNING;
LOG_LEVEL=DEBUG включает детали приложения, не всех библиотек сразу.

Runner Scrapy применяет общую настройку, запрещает установку дополнительного
root handler и повторно восстанавливает уровни после конструктора
CrawlerProcess. Перенаправление stdout в logging выключено. Это относится
к запуску через SpiderRunner, не к отдельной CLI-команде `scrapy crawl`.

Фильтр Celery переводит штатные сообщения о приёме/успехе задач на DEBUG:
они видны при LOG_LEVEL=DEBUG, но не засоряют обычный INFO. Из известных
штатных событий удаляются возвращаемый результат, аргументы и произвольный
текст исключения. Ошибки сохраняют безопасный стек, ID задачи и имя события.
Это фильтр конкретных шаблонов установленного Celery, а не универсальная
очистка любых сообщений библиотек. Дамп версий зависимостей Scrapy отключён.
Gunicorn/nginx access-логи, баннеры и остальные библиотечные сообщения пока
не нормализованы. Ротация остаётся в Docker.
HTTP middleware включён во всех окружениях и стоит первым, чтобы охватить
также ранние ответы других middleware. Access-записи nginx/Gunicorn остаются
отдельными источниками; этот этап их не отключает.

## Сквозной контекст

Реализация — `eazyclass/logging_context.py`. ContextVar хранит контекст текущей
операции отдельно для потоков/асинхронных контекстов. Фильтр общего console
handler добавляет его в каждую выводимую запись, включая старые сообщения;
в каждом вызове logger повторять идентификаторы не требуется. Контекст не
считывается из аргументов задачи, тела запроса или пользовательского профиля.

| Поле | Значение |
| --- | --- |
| `request_id` | Новый UUID для каждого HTTP-запроса |
| `task_id` | Идентификатор исполняемой задачи Celery |
| `task_name` | Имя исполняемой задачи Celery |
| `attempt` | Номер попытки задачи, начиная с 1 |
| `run_id` | Общий идентификатор корневого запуска и всех порождённых задач |

HTTP: сервер генерирует request_id самостоятельно и игнорирует входящий
X-Request-ID. Значение доступно как `request.request_id` и возвращается в
заголовке ответа `X-Request-ID`; CORS разрешает браузеру прочитать его.
Итоговая запись содержит шаблон маршрута, статус и duration_ms. Обычные
ответы, включая 4xx/5xx, дают access-событие INFO; диагностику ошибки пишет
её обработчик. Если исключение вышло из get_response напрямую, middleware
пишет безопасное ERROR-событие и передаёт исключение дальше.

Время измеряется до возврата объекта ответа, а не до получения всех байтов
клиентом. Ленивый рендеринг потокового ответа после выхода из middleware
не входит в этот контекст или длительность. Записи Gunicorn/nginx и сообщения
приёма задач в главном процессе worker не получают этот контекст автоматически.

Celery: before_task_publish переносит request_id/run_id в служебные заголовки
`eazyclass_request_id` и `eazyclass_run_id` протокола v2. При публикации новой
корневой задачи run_id равен её root_id или task_id. Дальше сохраняется тот
же run_id; это работает и для цепочек обновления расписания, и для задач,
порождаемых их этапами. Если корневой ID не UUID, создаётся отдельный UUID.
Внутренние заголовки принимают только UUID, произвольный текст отбрасывается.

task_prerun устанавливает контекст из заголовков и task.request; task_postrun
восстанавливает предыдущий контекст при успехе, ошибке и retry. Попытка равна
request.retries + 1. При retry task_id/run_id остаются теми же. worker_process_init
сбрасывает контекст, унаследованный при fork. Задача, запущенная Beat или вручную
без HTTP, имеет run_id/task_id, но не имеет request_id. Не следует выдумывать
request_id для фоновой работы.

Вызов `.run()` напрямую не проходит сигналы Celery. Режим eager `.apply()`
проходит сигналы исполнения, но не публикацию: для переноса контекста в этом
режиме заголовки требуется передавать явно. Штатная передача проверяется через
брокер, а не только через eager-тесты. Жёсткое завершение процесса не выполняет
finally, но новый worker начинает работу с пустым контекстом.

SpiderRunner передаёт копию текущего контекста отдельным аргументом Process.
Паук сохраняет run_id/task_id/attempt/request_id запускающей задачи, меняется
только service на `scrapy`. После завершения или исключения предыдущий контекст
восстанавливается. Идентификаторы не передаются как параметры самого паука.

Пример расследования: взять X-Request-ID из ответа API, найти записи запроса,
затем записи задач с тем же request_id. По их run_id собрать всю цепочку,
включая сообщения паука; по task_id и attempt отличить этап от его повторов.
Несколько независимых корневых задач из одного запроса имеют общий request_id,
но разные run_id. Эти значения служат только диагностике, не авторизации.

Проверка без внешних сервисов:

```text
python -m pytest scheduler/tests/test_logging_privacy.py scheduler/tests/test_logging_config.py scheduler/tests/test_logging_context.py scheduler/tests/test_schedule_logging.py --ds=scheduler.tests.logging_settings -p no:cacheprovider -q
```

Тесты проверяют оба формата, контекст, отсутствие секретов в обработчиках
авторизации, безопасный стек и отсутствие повторного вывода в отдельных
процессах с настройкой Django, Celery и запуском пустого Scrapy-паука.
Отдельный тест запускает Celery worker с брокером/результатами в памяти:
проверяет цепочку, retry и следующую независимую задачу после ошибки.
Дополнительно выполнена ручная проверка через docker exec в локальном
celery_worker: SpiderRunner запустил пустого паука отдельным Linux-процессом,
его запись содержала service=scrapy и все переданные идентификаторы/attempt.
Это проверка дочернего процесса в контейнере, не запуск задачи через рабочий
Redis-брокер. При bind mount для применения к работающим worker/beat требуется
перезапуск процессов; изменения переменных окружения на этом этапе не нужны.

## Ошибки и повторы

Один слой отвечает за диагностическую запись одного сбоя. Обычно это граница
запроса или задачи. Нижний слой передаёт исключение выше, если не обрабатывает
его сам. Не дублировать один traceback на каждом уровне и учитывать штатные
записи Django/Celery. Если исключение перехвачено и выполнение продолжается,
сохранить безопасную причину и отразить частичный результат в итоговой записи.

Различать `retry_scheduled` и окончательное `failed`; записывать номер попытки
и задержку. Итог задачи должен соответствовать её реальному результату.
Возврат функции, завершение дочернего процесса или запись сообщения «готово»
сами по себе не доказывают успешное выполнение бизнес-операции.

## Сбор с сайта и синхронизация занятий

На INFO остаются начало и итог сбора и синхронизации. Итог паука содержит
число разобранных групп, неизменившихся страниц, ранее обработанных групп,
ошибок, необработанных групп и занятий. Частичный результат — WARNING;
прерванный сбор, отсутствие любого успешного результата при ошибках и ошибка
сохранения — ERROR. Отсутствие групп — штатный пропуск. Детали отдельных
запросов, хешей, Redis-клиентов, маппинга и подготовки изменений — DEBUG.

Итог синхронизации с количеством добавленных/изменённых/удалённых занятий
пишется после формирования возвращаемого отчёта. Ошибка попытки и запрос retry
отмечаются WARNING, исчерпание попыток — ERROR; stage показывает, произошла
ошибка при загрузке/применении данных или при формировании отчёта. Этот итог
описывает применение полученных данных, не полноту исходного сбора: полнота
видна в итоговой записи паука. Ошибки кеширования после записи БД остаются
отдельными предупреждениями с объяснением последствий.

Исправлены два случая недостоверного успеха: ошибка чтения хеша Redis больше
не считается неизменившейся страницей; ошибка дочернего процесса/запуска Scrapy
или сохранения данных теперь прерывает задачу сбора. Runner проверяет Deferred,
флаг scrape_failed после закрытия и exitcode дочернего процесса. Частично
успешный сбор по-прежнему допускает синхронизацию полученных групп. Дочерний
процесс выводит безопасную ошибку и выходит с кодом 1 вместо сырого traceback.

Это проработка пути сайт → Redis → БД. Импорт Google-расписания, справочники
и рассылки остаются следующими отдельными участками. Содержимое Redis-ключей
и правила изменения занятий этим этапом не переработаны; конкурентные запуски
со shared Redis-ключами не получают изоляцию только благодаря run_id.

## Карта миграции модулей

Имена ниже — целевой каталог, не перечень уже внедрённых событий.

| Участок | События и полезный контекст | Вопрос для проверки |
| --- | --- | --- |
| HTTP, Django/DRF | `http.request.completed`: маршрут, статус, время, request_id | Почему запрос завершился ошибкой или был медленным? |
| Авторизация, nonce, refresh, logout | Результат, безопасная фиксированная причина, способ авторизации | На каком шаге отказано, есть ли сбой Redis? |
| Celery и цепочки обновления | Старт, retry, итог; run_id, task_id, attempt, очередь | Какая стадия не завершилась? |
| Scrapy | Итог обхода: запланировано, получено, без изменений, неудач, время | Все ли группы обработаны, доступен ли источник? |
| Синхронизация занятий | `schedule.sync.completed`: диапазон дат, группы, added/updated/removed, время | Что реально изменилось в БД? |
| Импорт Google-расписания, справочники | Прочитано, принято, пропущено, причины, добавлено/деактивировано | Данные полные и корректные? |
| Уведомления | Запланировано, отправлено, заблокировано, неудач, retry; период и run_id | Почему рассылка не дошла или дошла частично? |
| Бэкапы | Создание, выгрузка, ротация, итог, размер, время, попытка | Когда последний бэкап успешно выгружен? |
| Redis, менеджеры, формы, админка | Значимые изменения и сбои; технические детали на DEBUG | Какая пользовательская операция затронута? |

Последовательность: безопасность → общая настройка и контекст → обновление
расписания и справочников → уведомления → API и авторизация полностью → бэкапы
и оставшиеся модули → сбор, дашборды и оповещения.

Для каждого участка пройти нормальный сценарий, ожидаемый пропуск,
частичный/полный сбой и повтор, если применимо. Проверить истинность итога,
отсутствие секретов, дублирования и чрезмерного объёма. Регрессионные тесты
обязательны для защиты чувствительных данных и передачи контекста; не писать
тест на каждую формулировку сообщения.

## Метрики и эксплуатация — последующие этапы

Первые метрики: частота/длительность/ошибки HTTP, исходы и повторы задач,
возраст последней успешной синхронизации, покрытие групп, исходы доставки,
возраст последнего успешно выгруженного бэкапа. Уточнить, считаем ли попытки
или итоговые операции, чтобы повторы не искажали статистику.

Для Loki использовать небольшой набор меток: сервис, окружение, уровень.
Уникальные request_id, run_id, task_id и user_id оставлять полями записей,
не метками Loki/Prometheus. В метриках использовать шаблон маршрута вместо URL.

До подключения централизованного сбора определить срок хранения, права
доступа, лимиты объёма, ротацию и поведение при недоступном сборщике. Проверить
дублирование access-логов nginx/Gunicorn/Django и конфигурацию логирования
в отдельных процессах Celery/Scrapy. Текущий Docker `json-file` оборачивает
вывод контейнера, но не делает сообщения приложения структурированными.

Оповещения строить по последствиям: просроченное обновление/бэкап, устойчивые
ошибки, существенная недоставка. Единичный ожидаемый отказ не должен будить
администратора. Успешная выгрузка бэкапа не заменяет проверку восстановления.
