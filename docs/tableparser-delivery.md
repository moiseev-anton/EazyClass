# Полная цепочка и журнал доставки

Реализовано 7 октября 2026 в ветке `codex/tableparser-integration`.

`source_refresh_chain(source_id, start_day_offset=0, end_day_offset=None)` строит
цепочку: получение → разбор → публикация → обычная рассылка → административный
отчёт. Даты фиксируются при построении цепочки до получения листов и передаются
дальше как `resolved_range`. Задача `start_source_refresh` ставит такую цепочку
в очередь; её собственное завершение означает постановку, не завершение цепочки.

`publication_chain(revision_id, requested_by=..., automatic=False, ...)` строит
последние три этапа для явно выбранной сохранённой версии, в том числе исправленной
после ревью. Новая ручная публикация получает новый UUID. Повтор доставки задач
одной цепочки использует уже заданные UUID публикации и границы периода.
`source_parse_chain` по-прежнему доступна для получения/разбора без публикации.

Новая постановка dispatcher-задачи создаёт новую цепочку. Идемпотентность описана
для задач внутри построенной цепочки; атомарной транзакции между постановкой
дочерней цепочки в брокер и завершением dispatcher нет.

## Доставка

Миграция `0006` добавляет `PublicationDelivery`: отдельные этапы `notifications`
и `report`. Они создаются в транзакции применения публикации, поэтому необходимость
доставки сохраняется даже при потере следующей задачи. `superseded` пропускает
уведомления подписчикам, но имеет административный отчёт.

Доставка использует прежний `send_lessons_refresh_notifications` и выделенный
`deliver_admin_report`. Старый `send_admin_report` сохраняет прежний результат
для существующих цепочек. Отчёт теперь корректно обрабатывает типизированный
`NotificationSummary` после десериализации.

Перед внешним вызовом фиксируется `sending`. Успешно завершившийся вызов получает
`completed` с сохранённым результатом. Повтор задачи пропускает `completed` и
`skipped`, не повторяет изменение расписания и отправку. Статус `completed`
означает завершение попытки рассылки, а не доставку каждому адресату: прежний
notifier возвращает счётчики частичных ошибок, которые сохраняются в результате
и попадают в административный отчёт. Автоматической повторной отправки всей
рассылки из-за отдельных ошибок нет.

Если вызов выбросил исключение, статус становится `uncertain`; потеря процесса
может оставить `sending`. Автоматический повтор этих состояний запрещён: часть
сообщений могла уйти до ошибки. Это не гарантия exactly-once внешней доставки.
Существующие сетевые повторы Telegram notifier сохраняются, поэтому при
неопределённом сетевом исходе возможны дубли на его уровне.

Отчёт запускается после завершённого либо явно пропущенного этапа уведомлений. Ошибка административной
отправки не заставляет повторно отправлять уведомления подписчикам. Для зависших
и неопределённых состояний добавлены команды просмотра, возобновления и явного
решения оператора с журналом `DeliveryResolution`; см.
[tableparser-delivery-recovery.md](tableparser-delivery-recovery.md).
Действий GUI и периодического обработчика pending-записей пока нет.

## Отчёт и история

`PipelineSummary` дополнен метаданными публикации: UUID запуска, версии и
публикации, номер версии, период, статус, количество занятий с `needs_review`.
Обычные счётчики добавленных/изменённых/удалённых занятий и результаты рассылки
сохранены. Доступ к истории версий, публикаций и доставки зарегистрирован в
Django admin только для чтения, с обычными Django view permissions.

Если настроен `TABLEPARSER_PUBLIC_BASE_URL`, в отчёте есть ссылка на публикацию
в Django admin. Значение должно быть публичным адресом приложения без query и
fragment; секретов в нём быть не должно. Без адреса либо admin URL отчёт содержит
идентификаторы без выдуманной ссылки. Добавлены таблица ревью, редактирование
версий и явная публикация; см. [tableparser-admin-review.md](tableparser-admin-review.md).

Уведомления формируются существующим сервисом по сохранённому summary с
использованием текущих связанных объектов/подписок. Полного снимка адресатов и
готовых сообщений для каждой публикации сейчас нет. Поэтому доставка не должна
задерживаться на длительное время относительно последующих изменений справочников.

## Проверки

76 Django-тестов прошли на PostgreSQL 16: весь ingestion, прежние проверки
диапазона и аннотаций, повторы публикации/доставки, неопределённые исходы,
пропуск устаревшей публикации, метаданные отчёта и полный путь от получения до
отчёта. В сквозном тесте настоящий парсер и БД, подменены только получение листов
и отправители уведомлений. 18 прежних pytest-тестов Telegram notifier и обработки
ошибок также прошли. Было только предупреждение pytest о существующей неизвестной
настройке asyncio, не ошибка тестов.

Дополнительно проверена передача задач через Redis 7 и Celery worker с пулом
`solo` в отдельном потоке тестового процесса, с PostgreSQL 16. Полная цепочка
выполняется через `.apply_async()` и JSON-сериализацию. После остановки и нового
запуска worker повтор той же публикации не меняет расписание и не повторяет
отправителей. Ошибка отправителя оставляет `uncertain`, останавливает цепочку
до отчёта; повтор задачи через брокер возвращает `DeliveryUncertain` без отправки.

Воспроизведение и границы этой проверки описаны в
[tableparser-worker-validation.md](tableparser-worker-validation.md).
Сообщения не отправлялись, production-миграции и расписания beat не запускались.
Совместная установка зависимостей с TableParser 0.1.1 и повтор всех 78 тестов
в чистом Linux-venv также прошли. Затем добавлены восстановление доставки и
проверка SIGKILL отдельного solo-worker. Интерфейс ревью/публикации также добавлен;
после него общий прогон с admin содержит 101 успешный тест. Следующие этапы —
подготовка серверного выпуска и контролируемое внедрение.
