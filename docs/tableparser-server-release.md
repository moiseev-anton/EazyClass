# Выпуск TableParser на сервер

Обычная сборка теперь устанавливает пакет автоматически через основной Dockerfile.
Ресурсы 0.1.1 и первоначальные знания уже перенесены на production.
Повседневное обновление: [настройка окружения](tableparser-env-setup.md).
Примеры старых образов в отчётах ниже сохранены как история проверок.

## Что подготовлено

Сервер использует память в PostgreSQL. Неизменяемый комплект выпуска содержит
`runtime/` с настройками и обученными моделями, `image/` с wheel и закреплёнными
версиями зависимостей, `seed/knowledge.sqlite3` для первоначального импорта,
`release.json` с контрольными суммами. В `runtime/` нет рабочей SQLite.
Файл в `seed/` не используется при разборе и не заменяет PostgreSQL при обновлении.
Локальная версия TableParser продолжает работать со своей SQLite.

Комплект и его SHA256 передаются раздельно: доверенная контрольная сумма должна
быть взята из записи выпуска, а не вычислена заново из полученного манифеста.
Проверка обнаруживает также лишние файлы. Не сохранять логи внутри комплекта.
Снимок знаний содержит исторические данные: хранить комплект с теми же правами
доступа, что и резервные копии БД; не публиковать его в репозитории/образе.

Сборка из репозитория EazyClass (Python 3.12, без Django settings и сети):

```sh
python -m schedule_ingestion.release_bundle \
  --wheel /artifacts/eazyclass_tableparser-0.1.1-py3-none-any.whl \
  --wheel-sha256 32564a2e31d8993a8563a0ce041194f5bce049f6693f1895a13e9379b8c43c49 \
  --resources /artifacts/approved-runtime \
  --knowledge /artifacts/initial-knowledge.sqlite3 \
  --install-report /artifacts/install-report.json \
  --output /srv/tableparser/releases/RELEASE_ID
```

Сборщик принимает только новый каталог. Ресурсы копируются с проверкой хешей;
локальная SQLite из каталога ресурсов исключается, её хеш фиксируется отдельно.
Источник первоначальных знаний выбирается явно через `--knowledge`.
Использовать закрытый, зафиксированный снимок SQLite без WAL/SHM, а не живую БД.
Содержимое и схема снимка дополнительно проверяются командой импорта.

## Сборка образов

Указать TABLEPARSER_RELEASE_DIR в `.env`, затем из проверенного коммита:

```sh
docker compose build django celery-worker celery-beat flower
```

Dockerfile автоматически получает `image/` релиза через именованный контекст,
проверяет SHA256 wheel, устанавливает пакет и зависимости и выполняет `pip check`.
Модели и SQLite-снимок не включаются в образ: они подключаются отдельно.
Сборка требует сети для скачивания зависимостей; версии закреплены, но хеши всех
скачиваемых дистрибутивов не фиксируются. Конфликты requirements и релиза останавливают сборку.

Для обычного обновления на том же сервере дополнительных шагов с образами нет.
При переносе готовых образов на другой сервер присвоить итоговым образам Django
и worker отдельные теги выпуска, записать их ID, коммит приложения и SHA256 релиза.
Доставить через docker save/load или registry. На целевом сервере выбрать эти теги
через необязательный docker-compose.tableparser.yml и использовать `--no-build`.
Второй этап установки пакета поверх образа больше не требуется.

## Первый запуск: сначала репетиция на копии БД

1. Восстановить актуальную резервную копию EazyClass в изолированную PostgreSQL.
   Отключить внешние отправки и периодические задания. Проверить реальную историю
   миграций командой `python manage.py migrate --plan`: тестовая БД приложения
   не заменяет репетицию обновления существующей серверной схемы.
2. Подключить комплект только для чтения. Задать `TABLEPARSER_RESOURCE_ROOT`,
   `TABLEPARSER_CATALOG_SOURCE`, `TABLEPARSER_PUBLIC_BASE_URL`. Историческое
   пространство имён текущего снимка — `https://eazyclass.ru/api/v1`.
   Это ключ исторических исключений/дополнений, а не URL для загрузки справочника.
   Справочник читается из текущей БД, включая неактивные записи.
3. Выполнить миграции, проверить снимок, затем применить первоначальный импорт:

```sh
python manage.py migrate --noinput
python manage.py import_tableparser_knowledge /opt/tableparser-release/seed/knowledge.sqlite3
python manage.py import_tableparser_knowledge /opt/tableparser-release/seed/knowledge.sqlite3 --apply
python manage.py check_tableparser_release /opt/tableparser-release/release.json \
  --expected-sha256 APPROVED_MANIFEST_SHA256 --require-imported
python manage.py collectstatic --noinput
```

4. Проверить разбор сохранённого контрольного входа и интерфейс ревью без
   публикации. Полное совпадение с эталоном требует также прежних справочников,
   исходных листов и временного контекста. Проверка готовности сама ничего
   не скачивает, не разбирает, не синхронизирует и не рассылает.
5. После успешной репетиции согласовать окно серверного запуска. Остановить
   поступление задач старой цепочки, дождаться текущих операций и записать
   состояния незавершённых публикаций/доставок. Сделать резервную копию рабочей БД
   и сохранить предыдущие образы/ресурсы. Именно здесь накатываются миграции
   рабочей БД и выполняется первоначальный импорт — до старта новых workers.
6. Повторить проверку готовности уже в целевом окружении. Затем запустить новые
   процессы и проверить ручной цикл. Периодические задачи включаются отдельно,
   после выбора времени; одновременно старую и новую цепочки одного источника
   не запускать. Границы `(0, None)` / `(1, None)` сохраняют прежнюю семантику
   удаления отсутствующих занятий на всём заданном периоде.

Только для необязательного режима готовых образов подключить `docker-compose.tableparser.yml`. Переменные:

```text
TABLEPARSER_RELEASE_DIR=/srv/tableparser/releases/RELEASE_ID
TABLEPARSER_DJANGO_IMAGE=eazyclass-parser:RELEASE_ID
TABLEPARSER_WORKER_IMAGE=eazyclass-parser-worker:RELEASE_ID
TABLEPARSER_CATALOG_SOURCE=https://eazyclass.ru/api/v1
TABLEPARSER_PUBLIC_BASE_URL=https://YOUR_EAZYCLASS_HOST
```

Использовать оба файла при каждой команде (`docker compose -f docker-compose.yml
-f docker-compose.tableparser.yml ...`). Сначала `config --quiet`, затем одноразовые
команды через `run --rm --no-deps django python manage.py ...` на уже поднятой БД.
Включение процессов: `up -d --no-build django celery-worker celery-beat flower`.
В этом режиме `--no-build` сохраняет выбранные теги релиза без пересборки. Overlay сохраняет существующие тома static/media/rclone и LOG_SERVICE.
`collectstatic` выполнить из нового Django-образа в общий том статики перед
открытием обновлённой админки. Новые JS/CSS не появляются в production только
от замены образа; локальный runserver обслуживает их иначе.
Никакие записи PeriodicTask этим файлом не создаются.

## Следующие версии и откат

Для обновления собрать новый каталог и новые образы, проверить их на копии
текущей PostgreSQL и контрольных входах. Память не импортировать заново и не
заменять исходным снимком. Новые модели добавляются только как отдельно
проверенный выпуск; автоматического обучения при развёртывании нет.

Перед переключением завершить запуски старой версии: сохранённый ParseRun
закрепляет код и ресурсы, поэтому старый незавершённый разбор должен выполняться
старым worker либо заменяться новым запуском с новым манифестом. Для уже
созданных публикаций продолжать их UUID, не создавать дубликаты.

Откат кода/ресурсов возможен только при совместимой схеме PostgreSQL. Остановить
новые задачи, вернуть предыдущие образы и каталог, проверить готовность и
запустить процессы заново. Миграции вслепую назад не откатывать: сначала проверить
обратимость на копии. Восстановление резервной копии теряет изменения после неё
и требует отдельного решения; уже отправленные сообщения не отменяются.
Неопределённые доставки разбирать по `tableparser-delivery-recovery.md`.
