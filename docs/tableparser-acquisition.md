# Получение листов и Celery

Реализовано 7 октября 2026. `schedule_ingestion.tasks` автоматически обнаруживается
Celery как модуль задач установленного Django-приложения. Существующая цепочка
импорта CSV и синхронизации не менялась.

## Источник и загрузка

`ScheduleSource.sheet_names` задаёт имена листов для парсера, `sheet_gids` —
соответствие каждого имени числовому `gid`. Все имена и gid должны быть уникальны.
Миграция `0004` добавляет эту карту и уникальный `ParseRun.acquisition_id`.
Старые источники с пустой картой gid пригодны для ручного сохранения входов,
но не для автоматического получения: карту нужно заполнить явно.

Загрузчик использует тот же публичный GViz endpoint, что и локальный TableParser.
Новые OAuth-учётные данные и доступ к закрытым таблицам не добавлялись.
Идентификатор таблицы проверяется, адрес запроса всегда строится на docs.google.com.
На запрос заданы таймауты соединения/чтения 10/30 секунд.

Допускается только успешный HTTP-ответ и GViz status `ok` с корректными rows.
HTML авторизации, ошибки Google, отсутствие rows и повреждённые ячейки вызывают
ошибку. `rows: []` означает успешно полученный пустой лист. Нормализация ячеек
сохраняет поведение локального `build_raw_csv_rows`: приоритет форматированного
`f`, затем `v`, затем пустая строка; значения приводятся к строкам с trim.
Автоматическая интерпретация года здесь не выполняется — это задача парсера.

`acquire_source` читает конфигурацию, получает все листы и только затем атомарно
сохраняет запуск. Перед сохранением повторно проверяются включение источника,
таблица, список имён и карта gid. Изменение конфигурации отклоняет весь результат.
Это сравнение конечных значений: кратковременное изменение с возвратом к прежней
конфигурации отдельно не журналируется.

Дату для определения года задаёт начало получения в часовом поясе Django.
Листы загружаются последовательно; общего транзакционного снимка Google Sheets
между HTTP-запросами нет. Неизменившиеся листы входят в каждый запуск полностью.
При ошибке частичного успешного запуска не создаётся, повтор заново получает
все листы. Ошибки получения пока видны как ошибки Celery, отдельного журнала
по каждому HTTP-запросу нет.

UUID задачи получения служит `acquisition_id`. Повтор доставки после сохранения
возвращает прежний запуск без сетевого запроса. Конкурирующие доставки одного
запроса могут обе выполнить HTTP, но сохраняют только один полный запуск.
Новый UUID означает новое получение, даже если содержимое не изменилось.

## Задачи

Настройка Django `TABLEPARSER_RUNTIME` должна содержать `resource_root` и
`catalog_source`, описанные в `tableparser-execution.md`. Она пока намеренно
не заполнена рабочими путями проекта и не имеет скрытых значений по умолчанию.

- `fetch_source(source_id)` → UUID сохранённого запуска.
- `parse_run(run_id)` → UUID parser-версии выгрузки.
- `source_parse_chain(source_id)` строит цепочку из этих двух задач.
- `start_source_parse(source_id)` ставит новую цепочку в очередь и возвращает ID
  последней задачи; его завершение означает постановку, а не завершение разбора.

Задачи используют очередь `periodic_tasks`. Получение повторяется до трёх раз
с задержкой 60 секунд при сетевых ошибках, HTTP 408/429/5xx. Повреждённые ответы,
ошибки конфигурации и остальные HTTP-ошибки не повторяются автоматически.
Разбор повторяется автоматически только при `ParseBusy`; прочие ошибки требуют
разбора причины и явного повторного запуска/восстановления.

Цепочка передаёт конкретные UUID и не пишет в общие Redis-ключи расписания.
Публикация и рассылка к ней ещё не добавлены. Периодические записи beat не
создавались. При подключении будущей публикации период останется аргументами
задачи, с фиксацией границ для повторов и прежними правилами удаления.

## Проверки

На PostgreSQL 16 прошли 38 тестов всего приложения и отдельный дополнительный
сквозной тест цепочки. Он использует реальные сервисы получения/разбора/хранения,
установленный пакет парсера и подменяет только сеть. Проверены полный состав
листов, неполная загрузка, смена настроек во время получения, московская дата
около полуночи, повторная и одновременная доставка задачи, ответы Google и
остановка цепочки при ошибке получения.

Celery проверялся локальным `.apply()`, без брокера и отдельного worker.
Реальные HTTP-запросы к таблицам не выполнялись. Проверка с Redis/worker,
чистым серверным окружением и конкретным источником остаётся перед включением.
Временный PostgreSQL используется только для тестов; рабочая БД не изменялась.
