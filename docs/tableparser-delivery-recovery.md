# Возобновление публикации и решение по доставке

Возобновляется конкретный UUID `Publication`: её версия, подготовленные данные
и границы периода уже сохранены. Нового получения Google Sheets или разбора нет.
Для `pending` выполняется применение; для `applied`/`superseded` повторное применение
ничего не меняет. Завершённые и пропущенные этапы доставки не отправляются повторно.

Просмотр состояния (без отправки задач):

```text
python manage.py resume_publication PUBLICATION_UUID
```

Возобновление через Celery:

```text
python manage.py resume_publication PUBLICATION_UUID --enqueue
```

Команда выводит UUID публикации, статусы этапов, токены попыток и типы ошибок.
При `--enqueue` возвращает ID последней задачи цепочки. Статусы `sending` и
`uncertain` блокируют запуск до явного решения. Это проверка перед постановкой;
сами задачи также проверяют актуальное состояние под блокировкой БД.

## Неизвестный исход отправки

`sending` может означать работающий либо погибший процесс, `uncertain` — ошибку
после начала вызова отправителя. По одной записи нельзя установить, дошли ли
сообщения. Администратор сначала проверяет исход и состояние старого worker.

Доступны два решения: `skip` оставляет этап пропущенным; `retry` переводит его
в `pending` и разрешает новую попытку. При `retry` оператор принимает риск
повторения уже доставленных сообщений. Решение само не отправляет сообщений
и не ставит задачу в очередь.

```text
python manage.py resolve_publication_delivery PUBLICATION_UUID --phase notifications --decision skip --request-id NEW_UUID --expected-token ATTEMPT_UUID --actor ADMIN_NAME --reason "Проверен исход старой попытки" --worker-stopped
```

Для административного отчёта используется `--phase report`. Токен нужно взять
из результата просмотра состояния. `--worker-stopped` обязателен для `sending`:
это подтверждение оператора, что старый отправитель остановлен, а не команда
его остановки. Один только сброс токена не может остановить уже идущий внешний
вызов. После решения выполнить `resume_publication ... --enqueue`.

Новый `DeliveryResolution` хранит автора, причину, решение, исходное состояние,
токен, временные метки, результат и тип ошибки прежней попытки. Журнал доступен
в Django admin только для чтения. Журнал и изменение статуса записываются
одной транзакцией. Повтор того же `request-id` с теми же параметрами возвращает
прежнее решение; изменение параметров запрещено. Другой оператор с устаревшим
токеном не сможет сбросить новую попытку или завершённый этап.

При разрешении токен прежней попытки сбрасывается: позднее сохранение её результата
не изменит состояние новой попытки. Отчёт после `skip` уведомлений явно указывает,
что этап пропущен и доставка не подтверждена; фиктивных счётчиков доставки нет.

## Проверки и границы

Проверяются атомарность, повтор команд, устаревшие токены, конкурирующие решения,
возобновление с первоначальными датами и явный пропуск уведомлений.
`test_worker_crash` запускает отдельный Linux Celery-worker с `pool=solo`, имитирует
внешнюю отправку счётчиком в Redis и завершает процесс через SIGKILL до записи
результата. Новый worker не повторяет отправку; после решения оператора отчёт
завершается. Настоящие отправители в этом тесте заменены.

Для запуска нужен изолированный PostgreSQL и Redis, как описано в
`tableparser-worker-validation.md`. Worker для аварийного теста требует
`TABLEPARSER_CRASH_TEST=1` и использует только `test_tableparser_validation`.
Это проверка принудительного завершения отдельного solo-процесса, а не prefork
и не автоматической повторной выдачи unacked-сообщений брокером.

Автоматического периодического восстановителя пока нет. Прерывания до создания
`Publication` требуют продолжения соответствующего сохранённого запуска парсера;
команды этого документа работают с уже созданными публикациями. После длительного
простоя нужно учитывать, что прежний notifier использует текущие подписки и
связанные объекты; готовые сообщения и список адресатов не заморожены.
