# Запуск на Linux-сервере

Команды выполняются из корня обновлённого репозитория. Стек наблюдения отдельный;
его запуск не пересоздаёт Django/Celery. Дашборды и оповещения пока не включены.

## Настройки

Проверить `docker compose ls`, `free -h`, `df -h` и `docker system df`.
Записать точное имя существующего Compose-проекта приложения. Не запускать
автоматическую очистку Docker volumes: там могут находиться БД и сертификаты.

При первой установке скопировать `observability/.env.production.example`
в `observability/.env`. Исправить `APP_COMPOSE_PROJECT`. При обновлении уже
существующий `.env` не перезаписывать. Этот файл не содержит секретов приложения.

Создать отдельный пароль на сервере, не переносить локальный тестовый пароль:

```bash
umask 077
openssl rand -base64 24 > observability/grafana-admin.secret
sudo chown 472:472 observability/grafana-admin.secret
sudo chmod 400 observability/grafana-admin.secret
```

UID 472 — пользователь Grafana в закреплённом образе. Compose secret на Linux
монтирует файл: root-owned файл с правами 600 Grafana прочитать не сможет.
Пароль для входа можно прочитать через `sudo cat observability/grafana-admin.secret`.
Генерировать его только при первой установке: существующему пользователю пароль
меняют через Grafana, а не перезаписью файла.

Настройки приложения остаются в `.env` и `logging_config`. При `DEBUG=False`
форматтер по умолчанию выбирает JSON/INFO/production. Если значения заданы явно,
проверить `LOG_FORMAT=json`, `LOG_LEVEL=INFO`, `LOG_ENVIRONMENT=production`
в корневом `.env`, не выводя весь файл или `compose config` с секретами.
Основной и локальный Compose-файлы приложения в этом этапе не изменены.

Настройки приложения применяются при его обычном деплое и пересоздании
контейнеров. Если менялся код, включить пересборку образов. Не перезапускать
worker посреди важной задачи только ради запуска сборщика. JSON не обязателен
для самого сбора: старые текстовые строки также поступят в Loki.

Убедиться, что установлен обновлённый cron: `bash certbot/install_renewal.sh`.
Production-override монтирует `/var/log` только для чтения; Alloy выбирает из
него исключительно `certbot-renew.log`. Отсутствующий до первого запуска файл
допустим. Проверять сбор на следующем обычном запуске, не выпускать сертификаты
повторно ради теста.

## Проверка и запуск

Для коротких команд в текущей Bash-сессии определить функцию:

```bash
obs() {
  docker compose --env-file observability/.env \
    -f docker-compose.observability.yml \
    -f docker-compose.observability.prod.yml "$@"
}
obs config --quiet
obs pull
obs run --rm --no-deps alloy validate /etc/alloy/config.alloy
obs run --rm --no-deps loki -config.file=/etc/loki/config.yml -verify-config=true
obs up -d
obs ps
obs logs --tail=50
```

Функция `obs` существует только в этой сессии. Во всех последующих командах
на сервере использовать оба Compose-файла, иначе можно снять лимиты и подменить
каталог certbot локальным каталогом из базовой конфигурации.

С компьютера открыть SSH-туннель:

```bash
ssh -N -L 3001:127.0.0.1:3000 user@server
```

Открыть <http://localhost:3001>, войти как `admin`. Порт 3001 на компьютере
не конфликтует с локальной Grafana на 3000. На сервере Grafana привязана к
localhost; порты Loki и Alloy наружу не опубликованы. Публичный домен и Nginx
для первого запуска не требуются.

В Drilldown → Logs выбрать `production` и последние 15 минут. Проверить nginx,
django, celery-worker и другие активные сервисы. У тихого сервиса может не быть
записей за выбранный период. Обычный запрос к сайту даст access-запись nginx;
HTTP DEBUG-записи Django на INFO не ожидаются. Сверить новое известное сообщение
с `docker compose -f docker-compose.yml logs --since=5m <service>`.

## Начальные лимиты и контроль

| Сервис | Память | CPU, доля одного ядра |
| --- | --- | --- |
| Loki | 768 MiB | 0.75 |
| Alloy | 256 MiB | 0.25 |
| Grafana | 512 MiB | 0.50 |

Суммарный потолок памяти контейнеров — 1.5 GiB; это не резервирование памяти
и не гарантия достаточного запаса всему серверу. Swap этим контейнерам не
добавляется (`memswap_limit` равен `mem_limit`). При достижении лимита памяти
возможен OOM и перезапуск, CPU-лимит замедляет обработку. Ограничения стартовые,
а не доказанные пиковые требования. Передача логов не блокирует Django напрямую.

Первые дни проверять `obs stats --no-stream`, `free -h`, `df -h`, `obs ps -a`,
особенно во время паука/рассылок и поиска в Grafana. Перезапуски и OOM можно
проверить без вывода окружения:

```bash
for id in $(obs ps -q); do
  docker inspect --format '{{.Name}} restarts={{.RestartCount}} oom={{.State.OOMKilled}}' "$id"
done
obs exec -T loki du -sh /loki
```

Храним 7 дней, но это не квота диска. Учесть БД, бэкапы, Docker-логи и образы.
Если свободное место опускается ниже 20%, разобраться с ростом, не ждать заполнения.
Плановые обновления образов также требуют свободного места.

## Что происходит при сбоях

| Ситуация | Поведение |
| --- | --- |
| Alloy остановлен, Docker/cron продолжают писать | После запуска читает доступный источник с сохранённой позиции; записи старше 5ч55м отбрасываются |
| Loki временно недоступен | Alloy повторяет отправку до 120 раз, очередь в памяти; длительный сбой может привести к потерям |
| Alloy аварийно завершился с недоставленной очередью | Позиция чтения не равна подтверждению доставки; часть записей может потеряться |
| Docker удалил контейнер или ротировал непрочитанные записи | Автоматически восстановить их уже нельзя |
| Cron-файл ротирован во время долгого простоя Alloy | Старый архив автоматически не импортируется; при необходимости расследовать его отдельно |
| Сервер/диск утрачен | Стек на том же сервере тоже недоступен; volumes не являются внешним бэкапом |

Шестичасовое окно Loki согласовано с `max_chunk_age: 12h`: допустимое
запаздывание относительно последней записи потока равно половине этого значения.
Синхронизация времени сервера важна. Семь дней хранения не означают семь дней
восстановления. Повторные записи при сбоях возможны: exactly-once не обещается.

Для обычных диагностических логов на этом этапе принимаем эти ограничения.
Если понадобится гарантированная история аудита, её нельзя строить только на
данном сборщике. Экспериментальную WAL Alloy сейчас не включаем.

## Остановка и обновление

`obs down` останавливает только стек наблюдения и сохраняет volumes.
Не использовать `down --volumes`, если история и настройки нужны.
После изменения конфигураций перезапустить Loki, затем Alloy. Изменения
Compose/environment применять через `obs up -d`; обновление образов — сначала
`obs pull`, затем `obs up -d`. Перед сменой версий сохранить согласованные копии
volumes и проверить release notes: обратная совместимость БД не гарантирована.
